書き終えた記事を、公開手順が確実に読者へ届けるべきです。ビルド、アップロード、更新、確認を分ければ、失敗した場所もわかります。

## 明確な公開経路

現在のプロジェクトはローカルコマンドでビルドと公開を行い、静的ファイルをOSSへ送り、ESAで配信しています。CodeupとFlowの設定テンプレートは準備済みですが、実際のリポジトリーとクラウドのパイプラインはまだ接続していません。

Flowを設定するときも、次の順番を使えます。

1. npm ciでロックファイル通りに依存関係をインストールする。
2. npm run buildで型を確認してページを生成する。
3. 静的リソースを先に送り、HTMLとSitemapを公開する。
4. ESAのキャッシュを更新し、公開ページとビルド結果の一致を確認する。
5. 検索エンジンに通知し、成功状態を保存する。

## 内容によってキャッシュを分ける

内容のハッシュを持つファイルは長期間キャッシュできます。HTMLとSitemapは再検証し、公開後に更新するほうが古い内容を避けられます。

キャッシュ更新は非同期です。公開ページが新しい内容を返すことを確認してからURLを送れば、検索サービスが古い内容やエラーを見る可能性を減らせます。

## 失敗後に続けられるようにする

OSSの複数ファイルへのアップロードは原子的ではありません。途中で失敗しても、再実行で未完了部分を補えます。検索通知は成功したバッチを記録し、残った内容だけを後で処理します。

リクエストの受理は、記事のインデックス登録を意味しません。サイト公開と検索通知は別に確認します。設定と保守の詳細はプロジェクトのデプロイ文書を参照してください。
