![Matter ゲートウェイでは「点灯」と表示されるのに、照明が点かない：「成功」を誤報しない状態同期の設計](https://ay3s.com/images/covers/matter-confirmed-state.webp)

スマートフォンから照明への点灯命令は、Matter コントローラー、ゲートウェイ、シリアル接続のモジュール、無線デバイスを経由することがあります。各層が「成功」と返しても、それぞれが意味することは同じではありません。

キューがメッセージを受け付けたことは、無線で送信されたことを意味しません。モジュールが命令を受け付けたことは、ノードの状態が変わったことを意味しません。デバイスがオン・オフ状態を報告しても、発光素子が実際に光っている証拠とは限りません。

ゲートウェイが「メッセージのキューへの投入成功」の時点で外部向けの状態をオンに変えてしまうと、ユーザーに見えるのはデバイスの観測結果ではなく、期待した状態です。

本記事では、検証できる範囲に問題を絞ります。**非同期アダプター層で、命令の意図、デバイスの報告、結果が不明な状態をどう分け、順序の入れ替わり、重複、再起動をどう扱うか。** Python 標準ライブラリだけを使う実験を添付し、ローカルで実行済みです。この実験では Matter プロトコルスタックを動かしておらず、Bluetooth モジュールへの接続も実際の照明の制御も行っていません。ハードウェア間の相互運用性や認証の結果を示すものではありません。

## まず、失敗する経路を最後までたどる

照明の最後の報告がオフで、その後ユーザーがスマートフォンで点灯をタップしたと仮定します。

| 時点 | システムで起きたこと | この時点で確認できること |
| --- | --- | --- |
| T0 | デバイスがオフを報告 | その報告が表す時点で、デバイスの論理状態はオフ |
| T1 | ゲートウェイが点灯要求を受信 | 制御意図はオン |
| T2 | アダプターが命令を送信キューに入れる | キューが要求を受け付けた |
| T3 | シリアル接続のモジュールが受け付けたと返す | そのインターフェースの定義に従ってのみ解釈でき、デバイスでの実行成功へ勝手に格上げできない |
| T4 | 無線メッセージまたは状態応答が失われる | 命令が実行されたかどうかは不明な可能性がある |

最も起こりやすい誤りは、T2 で次の行を実行することです。

```python
reported_on = requested_on
```

これは「望む状態」をそのまま「報告された状態」として書き込みます。その後の通信経路で失敗が起きても、画面は先に完了を宣言してしまいます。

実験では、デバイスの報告状態を `False` で初期化し、`True` を要求しますが、デバイスからの応答は一切入力しません。楽観的な書き方では `True` と表示されますが、状態を分離したモデルでは `reported=False, pending=True` のままです。この違いを再現するのに、無線通信のパケット損失率や数百台のデバイスは必要ありません。要求の受け付けと動作の実行の間に非同期の境界があるだけで、問題は成立します。

## なぜ少なくとも三種類の情報を保持する必要があるのか

一つのブール値では、ユーザーの意図とデバイスから得た証拠を同時に表せません。実験で使う主なフィールドは次のとおりです。

```text
desired     デバイスに到達してほしい直近の状態
reported    最後に受け付けたデバイスの論理状態。未取得なら unknown
pending     現在も目標状態の観測を待っているか
timed_out   待機がタイムアウトしたか
session     現在信頼しているデバイスのセッション
sequence    現在のセッションで受け付けた最新の報告番号
```

命令を受け取ったときは、`desired` と待機状態だけを変更します。有効な報告を受け取ったときに初めて `reported` を変更します。タイムアウトした場合は今回の待機を終了し、「不明」と記録します。タイムアウトを自動的に「デバイスは実行しなかった」と読み替えてはいけません。

`reported=False` も、「今、確実にオフである」といつまでも解釈することはできません。実際のシステムには、報告の受信時刻、デバイスへの到達可能性、状態の有効期限に関する方針も必要です。この実験には有効期限の仕組みを実装していません。検証しているのは「最後に受け付けた報告が命令によって直接上書きされないこと」であり、「表示値が常にデバイスの実際の現在状態と一致すること」ではありません。

これらのフィールドは**本記事が提案するアダプター層の内部状態**であり、Matter の標準属性一式ではありません。Matter のインタラクションモデルは、コマンドの呼び出し、属性の読み取り、報告の購読を区別しています。[1] コマンドの結果を外部にどう返し、属性をどう更新し、ブリッジされたデバイスの到達可能性をどう表すかは、具体的なクラスター、SDK、下流プロトコルに合わせて設計する必要があります。本記事の `pending` を標準の OnOff ブール属性にそのまま入れることはできません。

制御アプリに「処理中」を表示する機能がない場合でも、少なくともゲートウェイ自身のログと診断画面には、この区別を残すべきです。

## デバイスが目標と同じ状態を報告しても、命令との因果関係は証明されない

ゲートウェイが点灯命令を送った直後に「オン」の報告を受け取ったとします。この場合、「デバイスが報告した論理状態は目標と一致する」とは言えます。

しかし、別のコントローラー、壁のスイッチ、過去の命令が存在するなら、その報告が今回の要求によって生じたとは限りません。命令前に生成され、命令後に届いた報告の可能性すらあります。

実験では、有効な報告が `desired` と等しいときに `pending` を終了します。その意味は「目標状態を観測した」だけです。**個々の命令に対する実行確認ではありません。** ある操作が実際に実行されたかを業務上知る必要があるなら、検証可能な要求識別子とそれに対応する結果など、十分な対応付け情報を下位プロトコルが提供する必要があります。オン・オフの値が一致しただけでは、因果関係は導けません。

これは点灯・消灯以外の操作で特に重要です。例えば「校正を一度実行する」は、単純な最終ブール状態ではないため、同じ完了判定を当てはめることはできません。

## 遅れて届いた古い報告は、なぜ画面を元に戻してしまうのか

次の具体的な経過を見てみましょう。

```text
報告 10：オフ
報告 11：オン
遅れて届いた報告 10：オフ
```

到着順に無条件で上書きすると、最終表示はオフになります。しかし、デバイスで報告が生成された順序では、より新しい状態はオンです。

実験では、同一デバイスセッション内で単調増加する番号を使い、`sequence > last_sequence` の報告だけを受け付けます。報告 11 の到着後は、重複した 11 も遅れて届いた 10 も拒否され、状態はオンのままです。

これには明確な前提があります。番号が実際に同じデバイス報告ストリームの順序を表し、その出所を信頼できなければなりません。ゲートウェイの受信カウンターでデバイスの順序を代用することはできません。受信カウンターでは、遅れて届いたパケットに、より大きな数字が割り当てられるだけです。

Matter の DataVersion や、何らかの無線プロトコルのシーケンス番号をそのまま流用してもいけません。カウンターによって適用範囲は異なり、クラスター、ネットワーク上の送信元、転送メッセージのいずれかに属する場合があります。自分の状態ストリームに使えるかどうかは、その定義、再送時の振る舞い、再起動時の規則を確認する必要があります。

## 再起動後に番号がゼロへ戻る場合、どの層の識別情報を扱うべきか

デバイスが再起動後に 0 から数え直し、ゲートウェイが前回の 100 を覚えたままだと、新しい報告を永久に拒否しかねません。

実験では、報告の識別情報を `session + sequence` に分けます。新しいセッションを明示的に確立した後、古い番号と古い報告を消去し、新しいセッションの報告 0 を受け付けます。同時に、古いセッションから遅れて届いた報告 99 は拒否します。

ここには省略できない制約があります。**パケットが新しい session を勝手に名乗っただけで、ゲートウェイが自動的に切り替えてはいけません。** セッションの確立には、信頼できる接続復旧、ハンドシェイク、またはデバイスの識別根拠が必要です。そうでなければ、偽造またはリプレイされたメッセージが「新しいセッション」を利用して保護状態をリセットできてしまいます。

モデルでは、`establish_session()` を明示的に呼ぶことで、この前提が満たされたことを表します。本人認証、鍵交換、カウンターの周回、ゲートウェイ自身の永続化状態からの復旧は実装していません。これらは実際のプロトコルに接続する前に補うべき作業です。

## 以前の平文ブロードキャスト実演を振り返る：内容の比較だけでは何が足りないか

当サイトで以前行ったパソコンとスマートフォンの実演では、上り方向のペイロードに `DV + アドレス + オン・オフ値` を使い、iPhone を使う経路では `DV0002:1` のようなデバイス名を使いました。[2] この種のペイロードには、報告番号も信頼できるセッション識別子もありません。

スマートフォンが同じ「オン」を繰り返しブロードキャストするとき、ペイロードが変化したかを比較すれば、同じ内容による繰り返しの上書きを減らすことは確かにできます。しかし、コード上の工夫では埋められない情報の欠落があります。

```text
同じ「オン」パケットが二つあっても、一つの古いデータの繰り返し送信かもしれない。
異なる時点に得られた、たまたま内容が同じ新しい観測が二つあるのかもしれない。
```

値しかなく、時刻や順序の根拠がなければ、受信側は両者を確実には区別できません。

実験では、内容による重複排除ロジックに `True` を二回入力し、一回だけ受け付けられます。この結果は重複排除が誤りだと証明するものではありません。重複排除によって「新しい観測かもしれない」という情報が捨てられることを示しています。内容による重複排除を状態の鮮度判定にも兼用することはできず、完全な状態整合性の仕組みとして説明すべきでもありません。

したがって、以前の実演における「内容が変化したときだけ報告する」は、その限定されたテスト場面には適していますが、製品レベルの順序入れ替わり対策としてそのまま一般化はできません。これは旧記事の結論の適用範囲を狭めるものであり、新たなハードウェアテストで得られた発見ではありません。

## 今回の実験の実行方法と、実際に得られた結果

添付ファイル：`matter_state_lab.py`。Python 3.10 以降が必要です。サードパーティーへの依存はなく、ネットワークへの接続もデバイスの制御も行いません。

```sh
python matter_state_lab.py
```

今回の実行では、6 組のアサーションがすべて通過し、出力は `matter_state_results.json` に保存されました。

| 実験シナリオ | 実際の出力またはアサーション結果 |
| --- | --- |
| 点灯要求を受け付けるが、報告は返さない | 楽観的な表示はオン。モデルは最後の報告「オフ」を保持し、待機中 |
| 待機がタイムアウト | 最後の報告は変わらず、実行結果は不明 |
| 遅延、重複、順序の入れ替わった報告 | 11 は受け付けられ、重複した 11 と古い 10 は拒否される |
| 目標はオフだが、先にオンが報告される | 待機を続け、その後のオフ報告で初めて目標状態を観測 |
| デバイスが新しいセッションを確立 | 古いセッションの 99 を拒否し、新しいセッションの 0 を受け付ける |
| 内容だけによる重複排除 | 同じ値の入力二つのうち一つだけを残し、新しい観測かどうかは判断できない |

これらは決定的なソフトウェアモデルのテストであり、実時間の測定、ネットワーク負荷、無線環境は含みません。設計に特定の情報が必要な理由は説明できますが、特定の Matter ゲートウェイにこれらの仕組みが実装されている証明にはなりません。

## モデルを実機につなぐ前に、何を収集すべきか

現場のログでは、少なくとも同じ要求について、要求の受信、キューへの投入、モジュールによる受け付け、デバイスからの報告、外部向け属性の更新という時点を分ける必要があります。各記録に対象デバイス、要求識別子（プロトコルが対応している場合）、報告元、セッション情報を付け、関連付けできない「success」だけの五行を残さないようにします。

そのうえで、隔離したテスト機器を使い、送信キューの失敗、無線応答の消失、報告の遅延、二つのコントローラーによる競合、デバイスの再起動、ゲートウェイの再起動をそれぞれ検証します。テスト時には実際の照明を観察します。製品要件として「発光」の証明が必要なら、適切な物理的観測が必要であり、論理的な OnOff 報告を照度センサーと同一視してはいけません。

下流側が順序を示す識別情報を提供しないデバイスについては、能動的な読み戻しや要求の直列化を検討できます。ただし、読み戻したデータが新しい問い合わせに由来するか、キャッシュされている可能性はないか、問い合わせ中に別の書き込みが起こり得るかも確認する必要があります。得られていない証拠に別の名前を付けて、確認済みと扱ってはいけません。

信頼できるゲートウェイの価値は、システムが実際にどの段階まで進んだかをユーザーと保守担当者が把握できることにあります。証拠が「要求を受け付けた」までしかないなら、早々に完了と表示するより、不明なままにしておくほうが診断しやすく、信頼にもつながります。
