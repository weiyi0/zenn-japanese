![AI に与えるコンテキストは、多いほど回答がよくなるのか？](https://ay3s.com/images/covers/ai-context-selection.webp)

あるタスクに何日も取り組み、チャット履歴がどんどん長くなっていく。AI が前のことを忘れるのではないかと心配になり、古い方針、エラーログ、修正履歴、参考資料をすべてもう一度渡して、最後にこう付け加える。「すべてのコンテキストを踏まえて続けてください」

これで情報は増える。しかし、AI が今何をすべきかを、より明確に理解できるとは限らない。古い方針はすでに廃止されているかもしれず、ログは修正前のものかもしれない。「完了済み」という記述も、以前の口頭での判断にすぎない可能性がある。

本当に整理すべきなのは、**この段階でどの事実に基づき、どの制約を守り、何を成果として出すか**だ。

以前、[「AI をもっと賢くしたいなら、まずモデルを替える前に」](https://ay3s.com/ja/articles/make-ai-smarter-before-changing-models/)でコンテキストエンジニアリングに触れた。今回は、それを長期タスクの引き継ぎと作業継続に当てはめる。この記事は公開されている研究と技術資料に基づき、2026 年 11 月 10 日に内容を確認した。本文中の比較案はまだ実施しておらず、効果向上を実測したデータは含まない。

## 入力できることと、安定して活用できることは違う

コンテキストウィンドウは、モデルが一度に受け取れる情報量を表す。しかし、その容量だけでは、各資料を正しく使えることの証明にはならない。

「Lost in the Middle」の研究では、複数文書を使った質問応答とキー・バリュー検索のタスクにおいて、関連情報の位置がテスト対象モデルの性能に影響し、長いコンテキストの中ほどにある場合は特に性能が低下しやすいことが示された。[1]

この研究は 2023 年に発表されたものであり、現在のすべてのモデルに同程度の問題があるとは言えないし、汎用的な「最適な文字数」も導けない。ここから得られる教訓は、長いコンテキストが有効かどうかは、宣伝されているウィンドウの大きさだけでなく、具体的なモデルとタスクでの結果を見て判断すべきだということだ。

Anthropic のコンテキストエンジニアリングに関する記事も、価値の高い情報を選び、タスクの進行に合わせてコンテキストを管理する重要性を強調している。単に短くするのではなく、期待する振る舞いを説明するのに十分な情報を残したうえで、冗長さを減らすという提案だ。[2]

例えば、相互参照のある契約条項を分析するなら、コンテキストを丸ごと残すことが重要かもしれない。一方、原因が特定できているボタンの不具合を修正する場合、無関係なモジュールのソースコードをすべて渡すことが、関連ファイル、再現手順、テスト結果を渡すより役立つとは限らない。

## 長い対話で最も混同しやすいのは「過去」と「現在」

ブログ記事をまとめているとして、記録に次の三つの発言があるとする。

> 初版：当面は公開しない。
>
> 第二版：ウェブサイトには公開してよい。
>
> 現在の要件：ウェブサイトには公開し、WeChat 公式アカウントと知乎では下書き保存のみ行う。

三つとも実際にあった発言だが、現在の作業を制約する内容は同じではない。引き継ぎ用の要約に「ユーザーは公開に同意した」とだけ書けば、公開先の範囲が抜け落ちる。初版だけを残せば、すでに許可された作業を止めてしまう。

これは「注意深く読んで」と一言付け足すだけでは解決しきれない。要約には現在有効な要件を書き、古い要件がどの決定によって置き換えられたかを明記すべきだ。

同様に、「保存 API を呼び出した」と「再度読み出し、下書きが存在することを確認した」も分けて記録する必要がある。前者は操作の記録であり、重複送信すべきか判断する証拠になるのは後者だ。

| 情報 | 推奨する保存方法 | 作業を再開する前にすること |
| --- | --- | --- |
| ユーザーの現在の目標と範囲 | 簡潔に列挙し、必要な原文や出典を残す | 後続のメッセージで範囲が変わっていないか確認する |
| 現在のファイルとバージョン | パス、バージョン、コミット識別子など | 実際のファイルを読む |
| 完了した操作 | 対象の識別子、応答、確認結果 | 曖昧な場合は結果を調べ、すぐにやり直さない |
| 失敗と未解決事項 | 具体的な失敗箇所、試した方法 | 未実行、実行失敗、結果不明を区別する |
| 過去の代替案 | 廃止した理由を明記してアーカイブに残す | 経緯を追う必要があるときに読む |

この表はタスクを整理するための提案であり、モデルの能力を保証するものではない。

## まず状態を要約し、後から確認できる入口を残す

役に立つ引き継ぎ資料は、短い要約と、後から確認できる資料で構成できる。

短い要約は「今どこまで進んでいるか」に答え、ファイル、ログ、リンクは「何を根拠にそう判断したか」に答える。両方を最初からすべてモデルのコンテキストに入れる必要はない。

Anthropic は、必要に応じて資料を読み込む方法を「just in time」戦略の一種と呼んでいる。パスなどの軽量な識別情報を残し、必要になったときに内容を読む方法だ。一方で、実行時に資料を探索するにはコストがかかり、所要時間が増える可能性も指摘している。検索手段が整っていなければ、モデルは重要な資料を見落とすかもしれない。[2]

したがって、AI にディレクトリだけを渡して、必ず答えを見つけられると考えてはいけない。次のように明確な索引を用意できる。

```text
タスク：記事 A のウェブサイト公開と、二つのプラットフォームでの下書き保存を完了する。
範囲：ウェブサイトは公開。WeChat と知乎は下書き保存のみ。
現在の版：本文ファイルのパスと、対応するカバー画像ファイル。
完了済み：ウェブサイトで公開済み。公開 URL と本文の確認記録は指定ファイルを参照。
未完了：知乎の下書きを再度読み出して確認する。
不明：保存リクエストが一度タイムアウトしたため、書き込まれたかどうか確認できていない。
次の手順：まずタイトルと元記事のリンクで下書きを検索し、結果を確認してから再試行するか決める。
受け入れ条件：公開ページと下書きの状態をそれぞれ報告し、すべて公開済みであるかのように混同して書かない。
```

これはテンプレート例であり、パスや応答は実際のデータで埋める必要がある。目標、状態、証拠、次の手順を分けて置くことで、「続ける」が何を意味するか明確になる。

## 圧縮するときに不確実性まで消さない

長期タスクには要約が必要だが、要約によって条件や留保が失われることがある。

「送信 API がタイムアウトし、結果はまだ確認できていない」が「送信に失敗した」に変わると、次の段階で重複作成するかもしれない。「ローカルプレビューだけを確認した」が「検証済み」になれば、その後のオンラインでの確認を飛ばすおそれがある。

Anthropic もコンテキストの圧縮について、圧縮しすぎると、後になって重要性が明らかになるような細かい条件が失われると注意を促している。[2]

比較的堅実なのは、要約で「観察済みの事実」「事実に基づく判断」「未確認の事項」を明確に分けることだ。要約を保存するときは出典を残し、タスクを再開するときは、次の行動を左右する状態を改めて確認する。

当初の受け入れ条件も残しておく必要がある。引き継ぎの要約を短くし続けた結果、「ページを仕上げる」だけになれば、もともと求められていたモバイル表示、アクセシビリティ用のラベル、保存時の動作が抜け落ちかねない。

## 回答が短くなっただけで、整理が有効だったとは判断しない

コンテキストの整理によって結果が改善したかどうかは、同種のタスクで比較する必要がある。

二種類の資料を用意できる。一方は元の記録をそのまま渡し、もう一方は現在の状態の要約と、必要に応じて読める参照元を渡す。両グループでモデル、タスクの要件、ツールの権限、受け入れ基準をそろえ、実際に読み込まれた資料を記録する。

比較では少なくとも、要件の見落とし、古い状態の参照、操作の重複、手戻りの回数、総所要時間、呼び出しコストを観察する。成功例を一つだけ選ばないこと。モデルの出力にはばらつきがあるため、複数回試したほうが参考になる。

反例も設計できる。多くの章を横断して照合するタスクでは、要約が必要な細部を削っていないか。ファイルの索引が不完全な場合、必要に応じた検索が全文を直接渡す方法より悪い結果にならないか。

**よいコンテキスト整理とは、無関係な資料を減らしながら、タスクの完了に必要な細部を守ることだ。** この二つが衝突するなら、まずタスクを検証可能な形で完了できることを優先し、どれだけ文字数を減らせたかはその後で考える。
