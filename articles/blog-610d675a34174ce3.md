スマートホームのデモでは、スマートフォンでの点灯、カーテンの連動、カメラ映像の表示がどれも滑らかに動く。しかし、5階建て、約1000平方メートルの住宅でより重要なのは、ある機器が故障したとき、家のどの機能が一緒に使えなくなるかという問題だ。

この記事では、まだ躯体工事の段階にある住宅プロジェクトで採用を検討している受け入れ検査方法を示す。現地での停電試験は実施していない。本文中の目標値は、施主、インテグレーター、施工業者が協議するための提案値であり、測定済みの結果でも業界の強制基準でもない。

シリーズの第1回では配線と容量の予算、第2回ではゲートウェイの選定を扱った。今回は「安定」を記録可能な要件に分解する。1回の故障で何が影響を受けたか、機器がいつ復旧したか、復旧後に誤動作しなかったか、である。付属のソフトウェアによる計算では、二つの落とし穴も示す。二つの経路が同じ故障点を共有している場合があること、そして見栄えのよいP95が多数の失敗を覆い隠す場合があることだ。計算データはすべて人工的に作成したもので、この住宅の試験データではない。

## 日常の機能ごとに依存関係を描く

壁のボタンによる操作がクラウドを経由し、さらにHome Assistantを通って、最後にMeshゲートウェイから照明を制御する必要があるとする。この場合、どれか一つの段階が機能しなくなるだけで点灯に影響する。壁に物理ボタンがあっても、独立した制御とは呼べない。

別の構成として、ローカルバインディングに対応したパネルが同じMeshネットワーク内の照明を直接制御し、中央コントローラーはシステム間の連携だけを担う方法がある。Bluetooth SIGが紹介する分散制御機能は、この構成の基盤になる。ただし、実際に成立するかどうかは製品と設定次第だ。[1]

そのため、受け入れ検査では先に機能を書き、次に依存関係を書く。

| 日常の機能 | 維持したいローカル機能 | 一時的に失ってもよいもの |
| --- | --- | --- |
| 壁スイッチでの点灯 | 中央コントローラーが停止しても操作できる | スマートフォンのシーン操作と遠隔操作は一時的に使えなくてもよい |
| エアコンの温度調節 | メーカー純正パネルが使える | 部屋をまたぐ統合制御は停止してもよい |
| 床暖房の温度制御 | 専用の温度制御と必要なインターロックが独立して動作する | スマート予熱は停止してもよい |
| カメラ録画 | NVRとカメラ用ネットワークが正常なら独立して録画する | 中央コントローラー上の映像カードは一時的に使えなくてもよい |
| 煙・ガスなどの警報 | 独立したローカル警報が引き続き有効である | ネットワーク障害によってスマートフォンへの通知が遅れる場合がある |

この表には、電源についての前提も明記しなければならない。家全体で商用電源が途絶えれば、バックアップ電源のない照明は点灯し続けられない。「中央コントローラーが故障しても点灯できる」と「家全体が停電しても点灯できる」は、まったく別の要件だ。

## ゲートウェイが二つあっても、なぜ同時に使えなくなるのか

ある階の遠隔制御経路を、簡略化したモデルで表す。

```text
経路A：中央コントローラー → コアスイッチ → 当該階のスイッチ → ゲートウェイA → 対象機器
経路B：中央コントローラー → コアスイッチ → 当該階のスイッチ → ゲートウェイB → 対象機器
```

両方の経路が設定済みで、実際に利用可能だと仮定する。ゲートウェイAだけを停止した場合、経路Bは動作を続けるかもしれない。しかし、当該階のスイッチが故障すれば、両方の経路が同時に途絶える。これは共通の依存先による単一障害点であり、ゲートウェイの台数を増やしても解決しない。

数理的には、ある機能は完全な経路が少なくとも一つ生きていれば利用できる。いずれかの経路上で必須の構成要素が一つ故障すると、その経路は途絶える。付属のスクリプトが行うのは、このブール論理の計算だけだ。ゲートウェイ一台の故障では経路が残り、共通のスイッチの故障では経路がなくなることを示す。無線経路の選択、再接続時間、実機による引き継ぎは模擬していないため、これをもってハードウェアにフェイルオーバー機能があるとは結論できない。

したがって、受け入れ検査には通信の依存関係図と電源の依存関係図の二つが必要だ。二台のスイッチが同じバックアップ電源のない電源タップにつながっていれば、電源障害を共有する。二つの中央コントローラーが同じホストマシン上で動いていれば、ホストの障害を共有する。重要なのは、どの障害に対して独立しているかであり、見た目上の機器の台数ではない。

## 外部ネットワークの切断だけを試験しない

WANを切断しても、中央コントローラーの故障時に動作することは証明できない。中央コントローラーを停止しても、階のスイッチが停電したときにネットワークが残ることは証明できない。受け入れ検査では、少なくとも次の手順を分けて実施する。

1. 外部ネットワークを切断し、LANと全機器への給電は維持して、ローカル操作を試す。
2. 外部ネットワークを復旧し、中央コントローラーのサービスを停止して、壁スイッチ、メーカー純正の温度制御、NVRを試す。
3. 中央コントローラーを復旧し、当該階のMeshゲートウェイだけを停止して、照明制御と階をまたぐシーンで、それぞれ何が失われるかを記録する。
4. Meshゲートウェイを復旧し、Threadボーダールーターを一台停止して、代表的なセンサーと制御機器を観察する。
5. 合意した試験時間帯に階のスイッチへの給電を止め、PoE機器に共通して生じる障害の範囲を記録する。
6. 専門担当者の手配に従って計画的な停電と復電を試し、誤動作、設定の消失、復旧順序を確認する。

毎回、導入する障害は一つだけにし、正常に戻してから次の項目に進む。空調設備の保護機能、人命に関わる警報、通電状態での施工は、むやみにケーブルを抜いて試験してはならない。それぞれの専門担当者が製品の手順に従って操作する必要がある。

試験のたびに、型番とファームウェア、ネットワーク設定、シーンのバージョン、機器一覧、設置場所、給電方法、状態報告間隔を含むベースラインを固定する。障害発生後はまずログを保存する。ルーター、ゲートウェイ、中央コントローラーをすぐに同時再起動すると、復旧してもどの操作が効いたのか分からなくなる。

復旧手順も計画に記載する。たとえば、先にスイッチとネットワークサービスを復旧し、次にゲートウェイと中央コントローラーを起動してから、機器の状態と予定タスクを確認する。具体的な順序は機器の文書に合わせて調整する。重要なのは、毎回同じ手順を実行し、そこからの逸脱を記録することだ。

## 「呼び出し成功」は、照明が実際に点いたことを意味しない

照明制御では、命令を発した時刻、プラットフォームが状態を受け取った時刻、現場で照明の変化を確認した時刻の三つを記録することを勧める。プラットフォームの実行履歴だけを記録すると、ゲートウェイは命令を受け取ったのに、その先で実行されなかった問題を見落とす可能性がある。

常用する壁スイッチ操作については、当初の目標として、合意した測定方法の下で応答の95%が500ミリ秒以内、一般的な部屋のシーンは2秒以内に完了、と設定できる。これは試案としての体験目標であり、サンプル設置での試験後に契約上確定すべきものだ。すべての機器の性能保証としてそのまま記載してはならない。調光時は、意図的に設定したフェード時間とネットワーク遅延を区別する必要がある。

代表的な設置箇所ごとに、少なくとも100回の管理された操作を行い、平均応答時間だけでなく、失敗、タイムアウト、重複実行を記録することを勧める。たとえば100回中1回失敗しても、平均遅延は依然としてよく見える場合がある。100回すべて成功したとしても、長期的な故障率がゼロという意味ではない。昼夜、高い同時実行負荷、長時間運転、異常からの復旧も対象にする必要がある。

## 「成功したサンプルのP95」に失敗を隠させない

100回操作し、90回は200ミリ秒で完了し、10回は2秒の期限までに目標状態を確認できなかったと仮定する。成功したサンプルだけでP95を計算すると、結果は依然として200ミリ秒で、「応答は非常に速い」と表現されやすい。しかし、期限内の成功率は90%にすぎない。

この記事では、総試行回数、期限内の成功回数、未確認の回数、成功したサンプルのP95という四つの値を併記することを勧める。P95にはnearest-rankの定義を用いる。成功したサンプルを遅延順に並べ、ceil(0.95×成功回数)番目を取る。成功したサンプルがない場合、P95は「データなし」と表示し、ゼロを入れてはならない。

10回の未確認サンプルを全体の並びで無限大とみなすと、この例における全体の95パーセンタイルは有限値にならない。実際の完了時刻は2秒より後かもしれないため、実際の報告では遅延を作り上げず、「全体のP95が2秒以内かどうかは判定できない」と書くのが適切だ。付属のスクリプトは誤読を避けるため、この二つの集計方法を両方残している。

未確認は、機器がまったく動作しなかったことを必ずしも意味しない。照明は点いたが報告が失われた場合も、報告は届いたが現場では点灯しなかった場合もある。現場での観察、プラットフォームからの報告、タイムアウトは別々に記録し、プラットフォーム上の状態をすべての証拠の代わりにしてはならない。

| 記録項目 | 目的 |
| --- | --- |
| run_id、機器番号、設定バージョン | 結果を同じ試験回にひも付ける |
| 障害条件と操作番号 | 通常試験、ゲートウェイ停止、復旧段階を区別する |
| 命令時刻、現場で変化した時刻、状態報告時刻 | 動作遅延とフィードバック遅延を分けて測る |
| 期限、期限前に確認できたか | 集計時にタイムアウトしたサンプルを残す |
| 重複動作、想定外の動作、復旧手順 | 最終状態だけを見て途中の誤りを見落とすことを防ぐ |

機器間でログの時計が同期していない場合、その時刻を直接引き算すると偽の遅延が生じうる。照明制御の体感速度は、ボタンと照明が同時に映る動画を撮り、フレーム単位で計時する方法がある。その際は撮影フレームレートと誤差を明記する。単一マシン上でのソフトウェア計時には単調時計を優先し、ログの壁時計時刻はイベントの照合に用いる。スマートフォンのストップウォッチだけでは、数百ミリ秒単位の指標の証明には適さない。

階全体のシーンでは、各照明が実際に完了した時刻と、そのばらつきを記録する。照明を一つずつ高頻度で問い合わせて余分な負荷を生み、その結果生じた輻輳を電波カバレッジの不足と誤認してはならない。

「復旧時間」についても、終点を定義する必要がある。ゲートウェイがオンライン一覧に再表示されても、部屋全体を正常に使えるとは限らない。たとえば、試験対象機器すべての状態を再確認し、基本操作が連続3回成功し、実行待ちの古い命令がないことを、その回の復旧条件として合意できる。ここでの3回は受け入れ検査手順の例であり、信頼性の証明ではない。

## 復旧後の誤動作は、オフラインのままでいるより見つけにくい

具体的な場面を考える。22:00の消灯予定タスクはネットワーク障害中に完了せず、住人が22:03に手動で点灯し、システムは22:05に復旧した。復旧処理が「22:00の消灯は未実行」としか判断しなければ、住人が点けたばかりの照明を消してしまう可能性がある。

この場合、まず業務上のルールを決める必要がある。期限切れのタスクにはまだ意味があるのか。手動操作は古い予定を取り消すのか。制御経路は操作元を判別できるのか。判別できない場合、どのような保守的な方針を取るのか。これらに全室共通の正解はない。寝室、廊下、庭で異なるルールを採用してもよいが、試験前に合意しておかなければならない。

少なくとも、人的介入なしでの復旧、障害中に誰かが手動操作した後の復旧、復旧中の再切断、という3組の復旧検査を追加する。最終状態だけでなく物理的な動作を毎回記録し、「いったん誤って消え、その後自動で点いた」ことが成功1回として扱われないようにする。

モーター、バルブ、空調設備では、命令の再送を標準の対処方法にしてはならない。状態の設定、相対移動、スイッチの切り替えでは、命令が重複実行された場合の結果が異なる。業務上の操作を安全に再試行できるかは、インターフェースの意味に照らして確認する必要がある。この記事が示すのは受け入れ検査の要件のみであり、具体的なアクチュエーターの保護とインターロックには、引き続きメーカーの設計上の制約が適用される。

## UPSは給電経路に沿って確認する

メインの機器ラックにUPSを設置しても、階のPoEカメラにバックアップ電源があるとは限らない。それらが階のスイッチから給電されるなら、そのスイッチもバックアップ電源の設計に含めるか、停電中はその区域で録画できないことを受け入れる必要がある。

重要負荷を200W、継続希望時間を30分とすると、負荷に必要なエネルギーは100Whになる。変換効率を0.85と仮定すれば、バッテリー側には約117.6Whの利用可能なエネルギーが必要だ。これには経年劣化、温度、放電特性はまだ含まれていない。最終的には、該当する出力でのUPSメーカーの稼働時間曲線を確認すべきだ。

受け入れ検査では、実際の継続時間、警告、シャットダウンの挙動を記録する必要がある。定格VAは選定パラメーターの一つであって、稼働時間ではない。NVRの正常なシャットダウンと録画の再開も、別途検証すべきだ。

## バックアップの受け入れ検査は、復元を終点とする

「バックアップタスクが成功と表示された」ことから分かるのは、何らかのバックアップが作られたということだけだ。中央コントローラーのデータ、Matterのペアリング情報、Threadネットワークの認証情報、Meshの設定データベース、メーカーのアカウントは、保存方法と復元方法がそれぞれ異なる場合がある。[2][3]

したがって、引き渡し資料には少なくとも、機器の型番とファームウェア、ネットワーク構成図、ケーブルとポートの対応表、設定ファイル、認証情報の保管場所、交換機器での復元手順を含める。ペアリングコード、アクセスキー、カメラの詳しい撮影範囲図を記事で公開してはならない。

復元訓練は隔離環境またはメンテナンス時間帯に実施し、同じ自動化を実行する二つの制御システムを同時に起動しないようにする。どのデータを復元できるか、どの機器に再認証が必要か、どの機能には依然としてメーカー純正アプリが必要かを記録する。バックアップの複製は自動的な高可用性ではなく、機器の再接続が不要になることも意味しない。

## 不具合を分類して引き渡し可否を決める

結果は、基本操作または保護機能の不具合、主要な体験が合意水準に達しないもの、付加機能の未完成、の3種類に分けたい。最初の二つは「今後ファームウェアを更新する」という説明だけで完了扱いにできず、是正措置、再試験、責任者を明確にする必要がある。付加機能の延期を認めるかどうかは、双方が書面で合意する。

たとえば、契約でローカルの独立操作を求めているのに、中央コントローラーの停止後に壁スイッチが使えなければ、基本機能の不合格となる。一方、あるブランド固有の照明効果が連携されていなくても、購入前に引き渡し範囲外と明示されていれば、後から不具合として扱うことはできない。受け入れ検査は要件と照合すべきであり、既存製品の能力に合わせて、その場で要件を逆に書き換えてはならない。

引き渡し時には、相互に対応する資料として、ベースライン設定、各回の生記録、不具合と再試験の記録の少なくとも3点を残す。試験していない組み合わせには「未実施」と書く。通常操作を100回通過しても、地下室の最も遠い地点や階全体での同時実行シーンの結果には代えられない。

受け入れ検査で最終的に引き渡すべきなのは、障害をどう発生させたか、現場で何を観察したか、復旧にどれだけかかったか、誰が対応を担当するかを記録した表だ。試験していない欄は「試験待ち」と書き、チェックマークによって設計目標を架空の実績に変えてはならない。
