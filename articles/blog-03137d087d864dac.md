![Matter と SIG Mesh の併用：5階建ての邸宅ではゲートウェイ数を何で決めるべきか？](https://ay3s.com/images/covers/villa-mixed-gateways.webp)

「各階にゲートウェイを1台」は初回の予算見積もりには適していますが、購入の根拠としては不十分です。5階建て、約1000平方メートルの邸宅では、まず各機器が何を制御し、その制御をどこで実行するかを決めてから、無線ネットワークへの接続口の数を決める必要があります。

本記事は、5階建ての未内装の邸宅についての初期設計を引き継ぐものです。具体的な機種も現地試験の結果もないため、特定のゲートウェイが何平方メートルをカバーできるとは主張しません。また、プロトコルの理論上の規模を製品の収容能力の代わりにはしません。

[シリーズ第1回](https://ay3s.com/ja/articles/villa-wireless-wiring-capacity/)では、配線、ポート、電力の予算を試算しました。今回は、購入時にさらに難しい問題を扱います。メーカーが「対応機器数」を示したとき、それが1フロア全体を支えるのに十分か、どう判断すればよいのでしょうか。後半には実行可能な計算スクリプトを添えていますが、検証するのは予算上の計算と論理関係であり、無線の実測結果ではありません。

## まず「ゲートウェイ」と呼ばれがちな3つの役割を分ける

Matter コントローラーは、アプリケーション層での管理と制御を担当します。Thread ボーダールーターは、Thread ネットワークを Ethernet や Wi-Fi が属する IP ネットワークに接続しますが、Matter コントローラーの代わりにはなりません。[1][2]

SIG Mesh ゲートウェイは、これらとは別の役割です。Matter Bridge に対応していれば、対応する配下の機器の機能を Matter コントローラーに公開できます。対応していなければ、ほかのサポートされたローカルインターフェースを介して接続する必要があります。ブリッジしても、元の Bluetooth 照明器具が Thread 機器になるわけではありません。

| 機器 | 確認すべきこと |
| --- | --- |
| Matter コントローラー | 対象の機器タイプを管理できるか。バックアップからどう復元するか。 |
| Thread ボーダールーター | ネットワーク認証情報をどう管理し、IP ネットワークにどう接続するか。故障時は何が引き継ぐか。 |
| SIG Mesh ゲートウェイ／Bridge | 実際に何台の機器を管理でき、どの属性をブリッジし、エリア間でどう連携するか。 |

1台の物理機器が複数の役割を兼ねることもありますが、製品が明確に対応している必要があります。名称だけで推測してはいけません。

混同しやすい数が、もう2つあります。Matter fabric と Thread ネットワークです。前者は制御プラットフォームの信頼・管理関係に、後者は無線ネットワークに対応します。同じ機器に Matter の制御プラットフォームをもう1つ追加しても、無線の経路が自動的に増えるわけではありません。逆に、Thread ボーダールーターを増やしても、Home Assistant の自動化ロジックが自動的に複製されるわけではありません。制御、伝送、自動化それぞれについて、冗長化の方法を説明する必要があります。

## まず機能ごとに役割を分け、すべての機器を遠回りさせない

この案では、照明制御は SIG Mesh を優先します。低消費電力のセンサーには Matter over Thread を使用できます。エアコンと床暖房には、文書がありメーカーがサポートするローカルインターフェースを優先します。カメラの録画は有線ネットワークと NVR が担います。

これは機器選定の出発点であり、プロトコルの性能順位ではありません。照明制御では、スイッチパネル、ドライバー、グループ化、調光の動作が一貫しているかを検証する必要があります。一方、空調・暖房では、運転状態の網羅性、ゾーンごとの制御、保護ロジックがより重要です。Home Assistant の公式資料も、機器のネイティブなローカル統合のほうが、Matter インターフェースより多くのメーカー固有機能を公開できる場合があると注意しています。[1]

製品が Matter に対応していても、「オン・オフできる」ことと「必要な機能がそろっている」ことは、項目ごとに分けて確認すべきです。たとえば、エアコンの設定温度は変更できても、必要な故障コードを取得できないかもしれません。照明器具の明るさは変えられても、メーカー独自のシーンを呼び出せないかもしれません。見積書には機能マトリクスを載せるべきで、対応プロトコルの表示だけでは足りません。

## 5台の SIG Mesh ゲートウェイは、5つの接続口なのか、5つのシステムなのか？

これは見積もりの段階で答えるべき問題です。

各階を独立したネットワークにすれば、ローカルの設定と故障範囲は比較的明確になりますが、階をまたぐ操作は上位層での協調に依存します。複数のゲートウェイを同じ Mesh ネットワークに参加させるなら、設定の共有、制御の協調、重複メッセージの処理をメーカーがサポートしているか確認しなければなりません。同じネットワークに、互換性を確認していないゲートウェイを勝手に追加してはいけません。

Bluetooth SIG の公式説明によると、Mesh はパブリッシュ／サブスクライブとマルチホップのメッセージ転送に対応し、すべてのロジックを中央コントローラーに置かずに分散制御を実現できます。[3] ただし、「プロトコル上は可能」と「購入したスイッチパネルが設定済み」は別です。中央コントローラーとゲートウェイを停止しても、パネルが照明器具を直接制御できるか検証する必要があります。

このプロジェクトでは、ひとまず各階にゲートウェイの接続口を1つ設ける前提で見積もりを取り、2か所目の設置候補も確保します。見積もり時には、メーカーに次の回答を求めます。

1. 機器数、エレメント数、実際の管理容量の制限と、ブリッジするエンドポイント数の制限。
2. パネルから照明器具を直接制御するための設定方法。
3. 同一ネットワーク内の複数ゲートウェイ、またはエリア別管理についての明確な構成。
4. シーンを実行する場所と、外部ネットワーク、中央コントローラー、ゲートウェイがそれぞれ停止した場合の違い。
5. 設定のバックアップ、ゲートウェイ交換、機器の再接続の手順。

階ごとに論理ネットワークを分けても、無線が互いに干渉しなくなるわけではありません。ノードが密集する場合は、リレー、再送、状態報告を調整する必要があります。常時給電の機器をすべてリレーに設定するだけで、信頼性が高まると考えてはいけません。

## 仮の機器リストで、「容量が足りる」の意味を計算する

ある階に照明ドライバー48台、パネル12台、センサー20台、合計80台の物理機器があると仮定します。これは説明用であり、この邸宅の照明器具リストではありません。

さらにメーカーが、ゲートウェイ1台あたり機器100台、エレメント200個、ブリッジするエンドポイント100個という仮の上限を示したとします。この例では、照明ドライバーは各1エレメント、パネルは各4エレメント、センサーは各1エレメントと仮定します。エレメントの合計は次のとおりです。

```text
物理機器：48 + 12 + 20 = 80
エレメント：48 × 1 + 12 × 4 + 20 × 1 = 116
ブリッジするエンドポイント：照明48台とセンサー20台だけを公開すると仮定し、計68
```

エレメント数とブリッジするエンドポイント数は、実際の製品の設定とマッピングから確認しなければなりません。「物理機器1台＝エレメント1個＝エンドポイント1個」と決めつけてはいけません。この例で68という数字になるのは、パネルをローカル制御層にとどめているためです。パネルのボタン操作イベントも上位層に提供するなら、結果は変わる可能性があります。

拡張の余地を残すため、次に定格上限の80%までしか使用しないと仮定します。これは「現在の必要量に20%を上乗せする」のとは異なる計算式です。

| 項目 | 必要量 | 定格上限 | 使用率80%で計算した利用可能量 | 初期判定 |
| --- | ---: | ---: | ---: | --- |
| 物理機器 | 80 | 100 | 80 | 計画上限にちょうど達する |
| エレメント | 116 | 200 | 160 | 余裕あり |
| ブリッジするエンドポイント | 68 | 100 | 80 | 余裕あり |

これらの負荷を複数の独立したゲートウェイに適切に分配できるなら、必要台数の下限は次のように書けます。

```text
容量から見た下限 = max(
  ceil(物理機器の必要量 / 利用可能な機器数),
  ceil(エレメントの必要量 / 利用可能なエレメント数),
  ceil(エンドポイントの必要量 / 利用可能なエンドポイント数)
)
```

この例の結果は1です。同種のセンサーをもう1台追加すると機器数は81台となり、定格の100台を超える前に、結果は2になります。

ただし、これは「負荷を分割でき、各ゲートウェイの容量が互いに独立している」場合に限られます。2台のゲートウェイが同じ機器一式をそれぞれ管理するなら、両方とも81台を収容する必要があるかもしれず、容量を合算することはできません。分割できない部屋のグループ自体が上限を超える場合も、切り上げ計算で問題を隠すことはできません。

したがって、計算表から得た1や2は容量から見た下限にすぎず、そのまま購入台数にはできません。カバー範囲、シーン実行時の負荷、製品の構成、故障範囲という制約も加味する必要があります。

## カバー範囲、負荷、故障時の引き継ぎは、3回に分けて検証する

1回目はカバー範囲です。選定した機器を実際の部屋に置き、ドアを閉め、通常の設置高さと向きで試験します。ノードをネットワークに参加させられる、あるいは時々制御できるだけでは、安定したカバー範囲の証明になりません。壁の仕上げ材、天井内の金属、機器収納盤の扉も条件を変え得るため、未内装の状態で試験に通っても、内装完了後に再試験が必要です。

2回目は負荷です。同じ階の照明48台のシーンを一斉に切り替え、同時にセンサーの報告と状態の返送を発生させます。照明を1台ずつ制御する場合と、グループアドレスで一度に制御する場合では、メッセージの形が異なります。実際にグループ制御を使っているか、大量の応答を同時に待つかは、ゲートウェイの実装とログで確認する必要があります。「照明48台＝無線パケット48個」と単純に見積もることも、機器数の上限だけから応答時間を推定することもできません。

3回目は故障時の引き継ぎです。接続口を1つ停止し、影響を受けた機器が別の接続口を経由して復旧するか確認します。2つ目の接続口も同じ階の PoE スイッチに依存しているなら、単一ゲートウェイの故障による影響は減らせても、スイッチの電源喪失には対処できません。

3種類の問題では、是正方法も異なります。カバー範囲が足りなければ、設置位置の変更や適切な転送ノードの追加が必要かもしれません。メッセージが輻輳するなら、不要な再送やポーリングを減らす必要があるかもしれません。故障時の引き継ぎに失敗したなら、予備経路と設定を確認すべきです。すべてを「ゲートウェイをもう1台追加する」で処理すると、費用をかけても元の問題が解決しないおそれがあります。

## Thread も、接続口を複数買えば自動的に冗長化されるわけではない

Home Assistant の文書では、1つの Thread ネットワークに複数のボーダールーターを設けられる一方、エコシステムによって設定方法は統一されていないと説明しています。[2] OpenThread の文書は、サービス発見や、基盤ネットワークを通じて Thread パーティションを接続する機能について説明しています。[4] 個々の市販機器が該当する機能を提供するか、どう有効化するかは、機種とファームウェアごとに確認が必要です。

各階にボーダールーターを1台置いても、厚い床スラブによって階同士の電波が届かないなら、ある階の接続口が停電したときに他の階が本当に引き継げるかを「まだ4台ある」というだけで判断することはできません。その階で最も遠いセンサーを使って電源断の試験を行い、到達性と復旧時間を記録すべきです。

モデル区画の段階では、まず隣接する2つの階で、認証情報の同期、ネットワーク参加、サービス発見、通常時のアクセス、ゲートウェイ故障、電源復旧を確認します。試験に通ってから5階全体に広げます。常時給電の機器についても、それ自体に Thread のルーティング機能があるか確認が必要です。電池式センサーを、階をまたぐ転送計画の支柱として最初から見込んではいけません。

この邸宅の Thread 接続口の数は、あらかじめ5台に固定せず、次の3つの現地での問いから決めます。地下2階で最も遠い機器は、その階の接続口に安定して到達できるか。接続口を1つ失った後、実際に到達できる経路はどれか。それらの経路は電源やスイッチを共有していないか。最初の問いだけに合格したなら「利用可能」とは言えます。残る2つにも合格して初めて、試験した故障条件下での冗長性を根拠をもって説明できます。

## Matter をまず同じ自動化用 VLAN に置く理由

まだ構成が確定していないこのプロジェクトでは、まず Matter コントローラー、関連する IP 機器、ボーダールーターの基盤ネットワーク側インターフェースを同じ自動化用ネットワークに置き、必要な IPv6 とマルチキャスト通信を確保します。ペアリングに使うスマートフォンは一時的に対応するネットワークに参加させ、完了後に日常利用時の経路を検証します。

これは、家全体のネットワーク分離をやめるという意味ではありません。カメラ、ゲスト、管理用インターフェースは引き続き分離できます。まず Matter の経路にある変数を減らし、その後でルールを一つずつ厳しくするためです。公式のトラブルシューティング資料は IPv6 によるローカル通信を明確に重視し、インターネット接続事業者による IPv6 インターネット接続は不要だと説明しています。[1]

## エアコンと床暖房：連携時に推測せずに済むよう、インターフェースの機能を見積書に明記する

「外出後、すべての部屋を省エネモードにする」必要があるなら、少なくとも操作対象、設定可能な値、返される状態、失敗時の動作を確認しなければなりません。サーモスタットの設定温度、室温、アクチュエーターの位置、主機の実際の運転状態は、それぞれ異なる情報です。そのうち1つを読み取れるだけで、システムに完全なフィードバックがあるとは言えません。

| 必ず確認すること | 検証可能な回答として受け入れられるもの | 受け入れるには不十分な回答 |
| --- | --- | --- |
| 制御経路 | インターフェースの型番、文書、ローカルでのアクセス方法を明示 | スマートホームに対応 |
| 状態の取得元 | 実機からの報告とゲートウェイのキャッシュを区別し、更新周期を説明 | アプリでは正常と表示される |
| 中央コントローラーのオフライン時 | 純正パネルとローカル温度制御が独立して動作することを現地で実演 | 理論上はオフラインにならない |
| コマンドの失敗 | タイムアウトを確認でき、未確認の値を実行済みとして表示しない | 送信に成功すれば成功 |
| 電源復旧 | 復旧時の方針を説明し、古いシーンが新しい手動設定を上書きしないようにする | デフォルトで自動復旧 |

ローカルインターフェースには、メーカー独自のプロトコルも、承認された標準インターフェースもあり得ます。機種の資料がない段階で「すべてのエアコンで Modbus が使える」と約束してはいけません。赤外線を代替手段にするなら、フィードバックの制約を明示すべきです。空調・暖房の凍結防止、過熱防止、ポンプとバルブのインターロックは引き続き該当する専門システムが担い、中央コントローラーは合意した範囲内でのみ運転方針を調整します。

## 予算上の数字を購入判断に変えるには、どんな証拠が必要か

まず施工業者にはゲートウェイの設置候補位置と配管・配線の予備確保表を渡し、サプライヤーには機能確認表を渡します。そのうえで、購入するのはモデル区画に必要な機器だけにします。モデル区画の結果には、各機種とファームウェア、容量の定義、ブリッジする属性の一覧、階をまたぐ負荷での動作、故障の影響、復旧手順を含めるべきです。

ゲートウェイ1台で容量が足りても、カバー範囲の試験に通らなければ、1台構成で購入することはできません。2台目を追加しても同じ故障経路を複製するだけなら、冗長化のための追加費用として計上することもできません。2つの案がどちらも要件を満たした場合に、保守の複雑さ、メーカーのサポート、交換費用、ライセンス費用を比較します。

最終的な購入台数は、機器の収容能力が十分か、各部屋のカバー範囲の試験に通ったか、接続口の故障後の影響を許容できるか、という3つの結果から導くべきです。階数は計画の出発点にすぎません。これら3項目の記録がなければ、「5台」も「10台」も未検証の数字です。
