![Zigbee と Thread は、1つの USB ゲートウェイを共用できる？](https://ay3s.com/images/covers/zigbee-thread-single-radio.webp)

すでに家には Zigbee のドア・窓センサーやスイッチがあり、これから Matter over Thread デバイスも追加しようとしている。USB アダプターを選ぶとき、チップの仕様に「Zigbee、Thread、マルチプロトコル対応」と書かれていると、1本買えば十分だと考えがちだ。

ここでは、3つの能力を区別する必要がある。ハードウェアが両方のプロトコルを実行できること、ファームウェアを切り替えてどちらか一方を使えること、そして稼働中の1つのシステムが2つのネットワークを同時に扱えることだ。

これらは同じ保証ではない。**共用する価値があるかどうかは、具体的なアダプター、ファームウェア、プラットフォームの対応方法による。**

本記事では Home Assistant の公式ドキュメントと Connect ZBT-1 を例に取り上げる。すべてのマルチプロトコル製品に当てはまるわけではなく、スループット、遅延、安定性の実測も行っていない。

## チップが両方のプロトコルに対応していても、挿すだけで同時に使えるとは限らない

Home Assistant の Thread ドキュメントによると、Thread と Zigbee は同じ IEEE 802.15.4 無線技術を使用するが、Thread は IP ネットワーク接続を提供する。Thread 自体は照明やセンサーの制御方法を定義しておらず、Matter や HomeKit などの上位プロトコルが別途必要になる。[1]

無線技術が共通しているため、対応チップで異なるプロトコルを実行できる可能性はある。しかし、それによって両方のデバイスが自動的に同じネットワークへ参加するわけではない。

Zigbee センサーは、近くに Thread ボーダールーターがあるだけで Thread デバイスに変わるわけではない。既存の Zigbee ネットワークには、引き続き対応するコーディネーターとソフトウェアのサポートが必要だ。

購入時には、少なくとも次の3つを個別に確認したい。

| 製品の説明 | さらに確認すべきこと |
| --- | --- |
| Zigbee と Thread に対応 | 異なるファームウェアを切り替えてどちらか一方を使うのか、同時に動作するのか |
| マルチプロトコルに対応 | どのファームウェアとプラットフォームを指すのか、まだ実験的な機能なのか |
| Matter に対応 | コントローラー、ブリッジ、Thread ネットワーク機能のどれを指すのか、それとも製品自体が Matter デバイスなのか |

無線チップの名前を見るだけでは、システム全体で最終的に何ができるかは分からない。

## Connect ZBT-1 に対する公式の見解は明確

Home Assistant Connect ZBT-1 は、以前は SkyConnect という名称だった。公式説明では、両者のハードウェアと機能は同じとされ、製品ページにはマルチプロトコルの状況も記載されている。[2]

本記事の確認時点でも、公式は1つの無線機で Zigbee と Thread に同時接続するマルチプロトコルファームウェアを実験的な機能と位置づけ、使用を推奨していない。ドキュメントによると、一部の状況では動作するものの、テストで確認された技術的な制約が使用体験を損なうため、Zigbee と Thread それぞれの専用ファームウェアを重視している。[2]

ここから言える具体的な結論は、ZBT-1 の公式推奨に沿って日常的に使うシステムを構築するなら、1つの無線機で2つのネットワークを同時に動かすことを標準案とすべきではない、ということだ。

一方で、すべてのチップ、すべてのプラットフォームでマルチプロトコルの安定稼働は不可能だ、という広すぎる結論は導けない。ほかの方式については、それぞれのハードウェアと保守状況を確認する必要があり、1つの製品ドキュメントだけで業界全体を判断することはできない。

製品ページには、ZBT-1 は生産終了となったものの、ソフトウェア更新は引き続き提供され、後継製品も案内されていると記されている。ここでは技術的な選択を説明するために取り上げており、旧モデルの購入を勧めるものではない。

## Thread 用に書き換えても、元の Zigbee ネットワークに機能が追加されるわけではない

専用ファームウェアを二者択一で使う方式では、Thread 用への変更は、その無線機に別の役割を担わせることを意味する。元の Zigbee デバイスには引き続き Zigbee ネットワークのサービスが必要であり、アダプターを Thread 用に書き換えるだけで自動的に移行できるわけではない。

そのアダプターが家庭内の Zigbee コーディネーターを担っている場合、サービスを停止してからファームウェアを書き換えると、既存デバイスの制御に影響する可能性がある。変更前に、プラットフォームのバックアップと移行手順、移行先のコーディネーターが対応する復元方法を確認すべきだ。

すべての Zigbee アダプターを問題なく交換できると決めつけてはいけない。また、通常の Home Assistant バックアップファイルを、検証済みの無線ネットワーク移行手段と同一視してはいけない。バックアップの範囲については、[バックアップの成功と復元の成功の違い](https://ay3s.com/ja/articles/home-assistant-backup-restore/)を参照できる。

新しい Thread デバイスを1台試したいだけなら、安定稼働している Zigbee ネットワーク全体に先に手を加えると、通常は問題の切り分け範囲が広がる。

## 1台のホストで2つのネットワークを管理できる。無線機まで1つにする必要はない

分かりやすい方法は、「同じ Home Assistant で管理すること」と「同じ無線機に担わせること」を分けて考えることだ。

Zigbee は専用アダプターに任せ、Thread の接続は別の対応する Thread ボーダールーターに提供させることができる。両者は引き続き Home Assistant のオートメーションに参加でき、基盤となるネットワークをそれぞれ維持するだけだ。

Thread ボーダールーターは、必ずしも Home Assistant ホストに挿す USB デバイスではない。公式ドキュメントにはサードパーティー製のボーダールーターが挙げられており、Home Assistant はそれらが提供するネットワーク接続を利用できると説明されている。ただし、具体的なデバイスの追加方法は、使用する上位プロトコルやスマートフォンなどの条件によって異なる。[1]

だからといって、Thread 対応スピーカーが家に1台あれば、準備がすべて整ったことにはならない。Thread ネットワークの認証情報、スマートフォンでのデバイス追加に必要な条件、Matter コントローラー、デバイスとコントローラー間のネットワーク到達性も確認する必要がある。

Thread ボーダールーターがすでに複数ある場合は、それらが同じ Thread ネットワークに属しているかどうかも区別したい。この点については、[複数のボーダールーターのネットワークと冗長性の関係](https://ay3s.com/ja/articles/thread-multiple-border-routers/)も参照できる。

## 無線機を分けても、無線の問題がすべて自動的に解消するわけではない

専用の無線機を使えば、1台の機器に複数の役割を担わせる複雑さは減らせる。しかし、2つのアダプターはどちらも実際の無線環境の中で動作する。

Connect ZBT-1 の公式ページでは、USB 延長ケーブルの役割が特に説明されている。USB 3.0 デバイスやポートの近くで発生するノイズは、Zigbee や Thread を含む 2.4 GHz 帯の無線機器に干渉し、ペアリングの失敗、接続切れ、タイムアウトとして現れる可能性がある。[2]

したがって、新しいアダプターを追加してから不安定になっても、すぐにプロトコルの非互換性が原因だと決めつけるべきではない。まず設置場所、接続、給電を確認し、各プラットフォームのドキュメントに従って無線環境を調べる。本記事ではチャネルの使用状況を測定しておらず、すべての家庭に当てはまる固定的なチャネルの組み合わせや設置間隔の数値は提示しない。

また、1回の調整でアダプターの交換、ファームウェアの変更、チャネルの変更、ネットワークの移行を同時に行うことも勧めない。1回に1項目ずつ変更するほうが、改善や悪化の原因を把握しやすい。

## まず役割を洗い出し、ハードウェアを追加するか決める

まず家庭内の機器を一覧にするとよい。Zigbee を管理しているのは何か、Thread ボーダールーターを提供しているのは何か、Matter コントローラーは何か、追加予定のデバイスはどの接続方式を使うのかを確認する。

既存の機器が適切な Thread ネットワーク機能を提供しているなら、USB アダプターをもう1本買う必要はないかもしれない。その機能が不足している場合は、「マルチプロトコル」という3文字だけで購入を決めず、現在のプラットフォームがサポートする専用の構成を評価する。

導入後の確認では、既存の Zigbee デバイスを引き続き制御できるか、新しい Thread デバイスを追加して使用できるか、関連コンポーネントの再起動後に復旧するか、問題が起きたときに以前の構成へ戻せるかを、それぞれ確かめたい。これは導入後の確認項目の提案であり、すでに実施したテスト結果ではない。

USB ポートを1つ節約できることには、もちろん価値がある。ただし、1本のアダプターに2つのネットワークの中核を担わせるなら、設定、問題の特定、復旧にかかるコストも考慮したい。機器選びの答えは、システム全体のサポート状況から判断すべきだ。
