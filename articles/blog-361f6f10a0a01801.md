![Matter デバイスをゲスト Wi-Fi に入れると、なぜか接続できなくなるのはなぜ？](https://ay3s.com/images/covers/matter-guest-wifi-isolation.webp)

スマートライトやスマートプラグ、その他の家電を専用のネットワークに分けるのは、家庭内ネットワークを整理するときによく行われることです。しかし、デバイスは Wi-Fi に接続でき、メーカーのアプリから遠隔操作もできるのに、Matter プラットフォームへの追加だけが最後の段階で失敗することがあります。

このような場合、すぐにデバイスをリセットしないでください。**「インターネットにアクセスできること」と「家庭内の Matter コントローラーから発見・アクセスできること」は、別の接続要件です。**

前回の[Matter と IPv6 に関する記事](https://ay3s.com/ja/articles/matter-ipv6-local-network/)では、プロトコルの基礎を説明しました。この記事ではゲストネットワーク、クライアント分離、VLAN に絞り、問題を層ごとに切り分ける方法を紹介します。資料の確認日は 2026 年 11 月 10 日です。以下はトラブルシューティングの提案であり、特定のルーターやハードウェア構成で実機検証した結果ではありません。

## ゲストネットワークがローカル制御を遮っている可能性

「ゲスト Wi-Fi」は、決まった一種類のネットワーク設定を指すわけではありません。ルーターによっては、ゲストにインターネットへのアクセスを許可する一方、メインの LAN へのアクセスを禁止します。さらに、無線クライアント同士の直接通信を禁止するものもあります。

したがって、デバイスがクラウドに接続できるのは、対応する外向きの通信経路があることを示すだけです。コントローラーがメインネットワークにあり、デバイスが隔離されたゲストネットワークにある場合、ローカル制御の経路は遮断されている可能性があります。

Matter の運用時の通信には IPv6 が使われ、ローカルでの発見には DNS-SD/mDNS が関わります。Home Assistant の公式トラブルシューティング文書は、VLAN、マルチキャストのフィルタリング、一部の不適切な IGMP snooping 設定が、Matter のセットアップ、発見、安定稼働に影響し得ると指摘しています。[1]

これは、すべてのゲストネットワークで Matter が使えないという意味ではありません。Wi-Fi の名前だけで、ネットワークが要件を満たしていると判断できないということです。ルーターで実際にどの分離ルールが有効になっているかを確認してください。

## スマートフォンでデバイスを検出できるのに、最後に失敗するのはなぜ？

初期設定と日常的な制御では、最初から最後までまったく同じ通信経路を使うわけではありません。

多くのデバイスは初期設定時に Bluetooth Low Energy を使い、スマートフォンによる発見と接続の確立を補助します。ネットワーク設定が完了すると、デバイスは Wi-Fi または Thread ネットワークに入り、その後の運用時の発見と通信は IP ネットワークに移ります。[1][2]

そのため、スマートフォンをデバイスの近くに置けばデバイスを検出でき、設定も開始できるのに、デバイスが接続先ネットワークに入った後、コントローラーが必要なローカル経路を通じてアクセスできない、ということが起こります。

この段階で電波の受信状態がよい別のスマートフォンに替えても、問題が解決するとは限りません。Bluetooth の段階を通過できたことは、その後の IPv6 とサービス発見の経路が利用可能である証拠にはなりません。

エラーがどの段階で起きるかを記録することをお勧めします。デバイスが見つからないのか、ネットワークに参加できないのか、参加後に発見できないのか、それとも制御中に断続的にオフラインになるのか。「設定に失敗した」とだけ記録すると、異なる問題が混ざってしまいます。

## mDNS 転送を追加しても、通信経路全体が通るとは限らない

VLAN をまたぐ場合、mDNS リフレクターや転送を有効にすることがよく提案されます。これはサービス発見の情報を元の境界の向こうへ届ける助けにはなりますが、その後の問題すべてを単独で解決するものではありません。

サービス発見によって、コントローラーはデバイスの接続情報を得ます。情報を得た後も、対応するアドレスにアクセスし、必要な通信を確立できなければなりません。Google の Matter 資料では、コミッショニング可能なデバイスの発見と運用時の発見を区別しており、運用時の発見は IP 上の DNS-SD に基づきます。[2]

したがって、少なくとも次の三つの層に分けて調べる必要があります。

| 層 | 確認すべきこと | その証拠の代わりにならないもの |
| --- | --- | --- |
| 発見 | コントローラーはデバイスのサービス情報を取得できるか？ | スマートフォンでパッケージの QR コードを読み取れること |
| 通信 | 対応する IPv6 アドレス、経路、アクセス制御は利用可能か？ | デバイスがメーカーのクラウドにアクセスできること |
| 権限 | コントローラーは正しい手順で制御権限を取得しているか？ | 二つのデバイスが同じ LAN にあること |

三つの層のうち一つが正常でも、残りの二つも正常だとは自動的に判断できません。

「ファイアウォールを恒久的に無効にする」ことを標準的な修正方法にしないでください。ネットワークセグメントをまたぐ構成では、具体的なデバイス、アドレス範囲、発見の仕組み、ポリシーの保守を踏まえる必要があります。汎用的なポート番号を列挙するだけでは、実際に必要な通信を見落としやすく、不要なアクセス範囲を広げるおそれもあります。

## Thread デバイスでは、ボーダールーターの接続先を確認する

Matter over Thread デバイスで確認すべきなのは、「この開閉センサーがどの Wi-Fi につながっているか」ではありません。開閉センサーは Thread を使用し、その無線ネットワークはボーダールーターを介して家庭内の IP ネットワークに接続されます。

ボーダールーターの Wi-Fi 側または Ethernet 側が隔離されたネットワークにある場合、コントローラーとの間の通信に支障が生じる可能性があります。

Home Assistant の公式文書は、Wi-Fi 接続の Matter デバイスとボーダールーターを Home Assistant と同じ VLAN に置くことを推奨しています。また、Thread デバイスが属するネットワークには、Home Assistant のある LAN に接続されたボーダールーターを少なくとも一台用意し、構成をできるだけ単純に保つことを勧めています。[1]

これは公式に推奨されるトラブルシューティングの基準であり、「プロトコル上、VLAN をまたぐことは絶対に禁止されている」という結論ではありません。複雑なネットワークを構築する前に、再現可能な単純な構成を確立すると、その後の不具合がデバイスの互換性によるものか、ネットワークポリシーによるものかを判断しやすくなります。

家庭内に複数のボーダールーターがある場合は、それぞれがどの Thread ネットワークに属するかも確認してください。二台あるというだけで、代替経路があると考えることはできません。この違いについては、[複数の Thread ボーダールーターに関する記事](https://ay3s.com/ja/articles/thread-multiple-border-routers/)を参照してください。

## 一度に変える条件は一つにし、比較できる基準構成を作る

以下では、一般的なテスト用のライトやプラグを例にします。最初のネットワーク変更を、ドアロックや警報器などの重要なデバイスで試すことはお勧めしません。

まず現在の構成を記録します。デバイスの型番とファームウェア、制御プラットフォームのバージョン、スマートフォンとコントローラーがそれぞれ接続しているネットワーク、Thread ボーダールーターを経由するかどうかを控えてください。現在のルールも記録し、元に戻せるようにします。

信頼できる管理下のテストネットワークで、プラットフォームの要件に従い、関係するデバイスが同じネットワークにあり、互いを発見してアクセスできる経路を用意します。デバイスの移動に再設定が必要な場合はメーカーの手順に従い、繰り返し工場出荷時の状態に戻すことを最初の手段にしないでください。

次に、デバイスを追加できるか、制御できるか、状態の変化が反映されるか、という三つの動作を確認します。再起動後に再び発見できるかも観察してください。これらの基本動作が正常なことを確認してから、目的の分離設定を段階的に追加します。

| 変更 | 再確認が必要なこと |
| --- | --- |
| 無線クライアント分離を有効にする | 同じネットワークのデバイス同士が、必要に応じて引き続きアクセスできるか |
| コントローラーまたはデバイスを別の VLAN に移す | 発見、IPv6 の経路、アクセスルール |
| マルチキャストの最適化設定を変更する | 初期設定時の発見と、運用中の再発見 |
| ボーダールーターの上流側ネットワークを変更する | Thread デバイスからコントローラーまでの経路 |

ある変更を加えて初めて問題が生じたなら、まずその変更を元に戻して再検証します。Wi-Fi、VLAN、ファイアウォール、マルチキャスト設定を一度に変えると、最終的に動作が回復しても、どの変更が実際に効いたのか判断しにくくなります。

## 分離の目的を「誰が誰にアクセスする必要があるか」まで具体化する

スマートデバイスを別のグループに分けることには管理上の価値があります。ただし、ネットワーク設計を「インターネットにつながればよい」で終わらせることはできません。ローカル制御には、コントローラーが必要とする通信関係も維持しなければなりません。

より実用的なのは、どのデバイス同士が発見・通信する必要があり、どのアクセスを制限すべきかを明確にしたうえで、ルーターとプラットフォームが対応する実装方法を選ぶことです。

Matter デバイスがゲストネットワークに接続できても使えない場合は、まずこのローカル経路を確認してください。どの層で途切れているかを特定してから、ネットワーク上の配置を変えるか、必要な範囲に限ってアクセスルールを調整するか、より単純な構成を使うかを決めます。
