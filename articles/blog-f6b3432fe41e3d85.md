AIアプリを公開した後に困るのは、「また間違えた」と言われても、どの工程が原因か説明できないことです。

検索が文書を見つけられなかったのか、プロンプトが条件を落としたのか。モデルが遅いのか、ツールのタイムアウトで三回再試行したのか。安いモデルで一回の料金を下げたのに、仕事全体では高くなったのか。

**Langfuseは、その疑問を一つの仕事の実行履歴につなぎます。** 呼び出し、入出力、時間、使用量、評価を見て、修正箇所を判断できます。ダッシュボードは入口であり、問題を直せることが価値です。

本文は**2026年10月11日に確認した公式資料とPython SDK 4.17.0**を基にしています。例は計測構造の説明で、実際のモデルを呼びません。架空の本番測定値や導入実績はありません。

## Trace・Observation・Sessionを分ける

| 概念 | 記録する範囲 | よくある誤り |
| --- | --- | --- |
| Trace | 一回の質問応答やAgent実行 | 一日分の要求をまとめる |
| Observation | 検索、モデル呼び出し、ツール操作など一工程 | 最終回答だけ残す |
| Session | 複数ターンや連続する仕事 | 個々の仕事の境界を置き換える |

質問一回をTraceにし、検索と生成を子の工程にします。複数ターンはSessionで関連付けます。現行SDKはOpenTelemetryに基づくため、名前より正しいコンテキスト伝播が大切です。

Agentのループ全体を一つのgenerationで包まないでください。モデル呼び出しごとに記録し、ツールを対応する工程に関連付けます。合計だけでは、どの結果がコンテキストを膨らませたか分かりません。

## 最初は一つの処理で十分

小さなRAGの入口から始めます。

```text
answer-question
├── retrieve-documents
└── draft-answer
```

ルートに質問と最終結果、検索に文書ID・版・渡した本文、generationにモデルの入出力と実使用量を記録します。

`retrieve-documents`のような安定した名前を使います。注文番号、質問、要求IDは名前ではなく属性へ。公開版、環境、プロンプト版を加えると変更前後を比較できます。

## Pythonの最小例

**SDK 4.17.0**に固定し、Python 3.10以上を使います。SDKとサーバーの版、対応機能は別々に確認し、古い教程のメソッドを混ぜないでください。

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install "langfuse==4.17.0"

export LANGFUSE_PUBLIC_KEY="pk-lf-REPLACE_ME"
export LANGFUSE_SECRET_KEY="sk-lf-REPLACE_ME"
export LANGFUSE_BASE_URL="https://cloud.langfuse.com"
```

鍵はプロジェクト設定で取得します。BASE_URLは欧州Cloudです。他地域や自社運用では変更します。秘密鍵はサーバー環境変数に置きます。.envを書くだけではPythonは読み込まないため、ここでは明示的にexportしています。

`trace_demo.py`として保存し、`python trace_demo.py`を実行します。

```python
from langfuse import get_client

langfuse = get_client()
question = "How long are repeat article visits deduplicated?"

with langfuse.start_as_current_observation(
    as_type="span",
    name="answer-question",
    input={"question": question},
    metadata={"release": "demo-v1", "environment": "development"},
) as root:
    with langfuse.start_as_current_observation(
        as_type="span", name="retrieve-documents", input=question
    ) as retrieval:
        documents = [{"id": "privacy-v1", "text": "Repeat visits count once within 30 minutes."}]
        retrieval.update(output=documents)

    with langfuse.start_as_current_observation(
        as_type="generation",
        name="draft-answer",
        input={"question": question, "documents": documents},
        metadata={"simulation": True},
    ) as generation:
        answer = "Repeat visits count once within 30 minutes. [privacy-v1]"
        generation.update(output=answer)

    root.update(output={"answer": answer})

langfuse.flush()
```

文書と回答は固定データで、`simulation=True`が模擬実行を示します。モデル要求も架空のToken・料金も記録しません。実運用では検索関数とモデル呼び出しに置き換え、実際のモデルIDと応答のusageを記録します。

短いスクリプトは終了前に`flush()`を呼びます。常駐サービスではライフサイクルで扱い、Tokenや小工程ごとに強制送信しません。非同期処理、スレッド、キューの伝播も検証します。context managerだけでプロセス間の連続性は保証されません。

## Traceで何を見るか

利用者が誤りを確認した要求から調べます。

1. **入力条件**：製品型番、日付、対象版が欠けていないか。
2. **検索**：関連性、更新状況、分割で失った条件。
3. **モデル**：実際の文脈、予期しない再試行。
4. **ツール**：HTTP成功が業務操作の完了を意味するか。

各工程と全体時間を測ります。ストリーミングでは最初のTokenと完了を分けます。料金は全呼び出しと再試行を含めます。推計は価格設定とusageに依存するので、最終請求は提供元と照合します。

Langfuseは回答の正しさや業務権限を保証しません。権限外の試行を表示できても、阻止できるとは限りません。認証、引数検証、冪等性、書き込み確認はアプリ側で実装します。

## プロンプト管理：使った版を残す

編集画面に移すだけでは不十分です。版と呼び出しを結び、問題を再現し変更を比較します。

`support-answer`というtext promptを作り、`{{question}}`と`{{context}}`を使います。検証した版にproductionを付けます。

```python
prompt = langfuse.get_prompt("support-answer", label="production")
compiled = prompt.compile(question=question, context=documents[0]["text"])
```

`compile`は変数置換であり、モデル実行ではありません。productionは明示的に選んだ公開版です。新版を作るだけで本番に反映してはいけません。返されたpromptオブジェクトを統合方法に従ってgenerationに関連付けます。

キャッシュがあっても初回取得、更新、障害は残ります。重要な業務では起動時の事前取得と検証済みの代替プロンプトを用意し、切り替わった事実をログに残します。

## 評価：失敗を回帰確認にする

まず実際の匿名化した二十〜三十例を集めます。通常・曖昧な質問、資料不足、ツールの時間切れ、回答すべきでない質問を含めます。期待する動作を決めてからモデル、プロンプト、検索を比較します。

| 方法 | 用途 | 注意点 |
| --- | --- | --- |
| 決定的なコード検査 | JSON、必須項目、業務条件 | 形式が正しく内容が誤る |
| 人の注釈 | 専門判断、境界例、基準調整 | 基準の不一致と費用 |
| LLM-as-a-Judge | 明確な尺度による大量評価 | 偏り、不安定な点数、評価費用 |

オンライン評価は実トラフィックを監視し、オフライン実験は固定Datasetで候補を比べます。併用し、重要な失敗を平均点で隠さないこと。モデル採点は人の注釈と照合し、権限や重要規則は明確なコード検査を残します。

評価にも料金がかかります。抽出率、評価モデル、頻度を一緒に計算し、監視が業務より高くなる事態を避けます。

## Cloudか自社運用か

効果確認はCloudのテスト環境と匿名化したデータで始められます。本番データの送信可否は事前に判断します。自社運用は配置とデータ経路を管理できますが、一つのコンテナを起動して終わりではありません。

現行構成はWeb、Worker、PostgreSQL、ClickHouse、Redis/Valkey、S3/Blobです。PostgreSQLは取引データ、ClickHouseは観測データ、キャッシュはキュー、オブジェクト保存は元イベントと複数媒体の添付を担当します。

公式Docker Composeはローカル利用とテスト向けで、高可用性・拡張・バックアップを標準では提供しません。本番ではTLS、認証、DBとオブジェクトのバックアップ、キュー滞留、容量、保管期間、更新時の復旧を扱います。

オープンソースの核とライセンスが必要なEnterprise追加機能を分けます。Cloudのプラン・制限と自社運用費は別物です。未確認の価格だけで総費用を計算しません。

## 送信前にマスキングする

Traceには質問、資料、ツール引数、回答が集まり、普通のログより機密性が高くなります。実メール、電話番号、Token、内部ファイル全文を初期設定で収集しないでください。

アプリを離れる前に秘匿化します。現行Python文書は新規設定に`mask_otel_spans`を推奨し、SDKと他社計測のOpenTelemetry属性を対象にします。旧`mask`は対象が異なります。自動統合が記録する内容も確認します。

一つの処理で通常要求、失敗、スクリプト終了を確認し、送信内容とプロジェクト権限を点検してから範囲を広げます。

**最初の目標は、誤回答の要求を見つけ、原因を説明し、次の公開前の確認に変えること。** そこまでできれば、Langfuseは単なるAI看板ではありません。
