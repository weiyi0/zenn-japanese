![Home Assistantのタイマーで照明を消す、本当の難しさ：再起動後の補完実行で、なぜ二度実行され得るのか？](https://ay3s.com/images/covers/home-assistant-restart-delay.webp)

前回は、Home Assistantの再起動によって`for`や実行中の遅延が中断されることを取り上げました。最も自然な対策は、期限を保存し、起動後に期限切れのタスクを確認することです。

しかし、期限が解決するのは「いつ実行すべきか」だけです。さらに難しい問題があります。**動作は終わったのに、システムが完了を記録する前に止まった場合、再起動後はどうすべきでしょうか？**

再試行すれば重複実行の可能性があり、再試行しなければ、実際にはまだ実行されていないタスクを取りこぼす可能性があります。時刻をヘルパーに書き込んでも、この矛盾は自動的には解消しません。

この記事では、SQLiteと模擬照明を使った障害注入実験を通じて、一般的な照明用途での判断を考えます。スクリプトは実際に実行しましたが、Home Assistantの統合テストではなく、実際の家庭の機器も制御していません。示す状態機械は設計上の参考であり、そのまま貼り付けられる完全なYAMLではありません。

## まず、似て見える二つのルールを区別する

「10分後に照明を消す」は、二つの異なる業務上の意味を持ち得ます。

| ルール | 重視する事実 | 停止中に生じる情報の欠落 |
| --- | --- | --- |
| 部屋が10分間連続して無人なら消灯する | その間ずっと無人だったこと | 停止中に誰かが入室したか、システムには分からない可能性がある |
| ユーザーが10分のカウントダウンを開始し、期限に消灯を試みる | 期限と実行時の条件 | 期限を逃す可能性があり、実行結果が記録されない可能性もある |

この二つのルールは入れ替えられません。

一つ目では、過去のタイムスタンプを復元しても、停止中ずっと無人だったとは証明できません。独立した信頼できるセンサー履歴がなければ、一定時間の観測をやり直すのが保守的な方針です。

この記事の実験が対象にするのは二つ目です。**ユーザーが明示的に消灯タイマーのタスクを作成し、期限後に十分新しい「無人」の観測が得られた場合に限り、通常のテスト用照明を消そうとします。** 停止中の在室状況が連続してどうだったかを復元できたとは主張しません。

## 日時ヘルパー一つだけでは足りない理由

Home Assistantの`input_datetime`は日付と時刻を保存できます。公式ドキュメントによると、有効な`initial`を設定した場合はその値から開始し、そうでなければ停止前の状態を復元します。[1]

期限の記録には適していますが、「期限は昨日の午後10時」という情報だけでは、そのタスクがまだ有効かどうかは分かりません。すでに完了したかもしれず、ユーザーがキャンセルしたかもしれず、前回のカウントダウンのものかもしれません。

そのため、少なくともタスクの識別子、期限、状態の三つを表す必要があります。例えば次のような情報です。

```text
id=42
due=明確に定めた期限
state=pending
```

`id`は新旧のタスクを区別し、`due`はいつ実行を試みられるかの判断に使い、`state`は実行待ち、完了、キャンセルを区別します。

Home Assistantでは、複数のヘルパーで同様の情報を表せますが、それらの更新をそのまま一つのデータベーストランザクションとみなすことはできません。「すべて成功するか、すべて失敗するか」に厳密に依存するなら、対応する永続化機能とトランザクション機能を持つコンポーネントを使用し、復元時の動作を検証すべきです。この記事でSQLiteを使うのは、この問題を画面上の設定から切り離して調べるためであり、Home Assistant自身のデータベースを直接変更する提案ではありません。

## 無視できない中断の隙間

期限に達し、次の流れで実行するとします。

```text
pendingのタスクを読み取る
現在の条件を確認する
消灯動作を送信する
タスクをdoneに更新する
```

3番目の後、4番目の前にプログラムが中断すると、照明はすでに消えているかもしれませんが、ディスク上のタスクは`pending`のままです。再起動後に見える記録は、「動作を送信する前に中断した」場合とまったく同じになり得ます。

順番を逆にしても根本的には解決しません。先に`done`を書き込み、その後で消灯する場合、二つの処理の間に中断すると、タスクは完了として記録されても照明は点いたままです。

| 記録の順序 | 中断の隙間 | 復旧時のリスク |
| --- | --- | --- |
| 先に完了を記録し、その後で実行 | 完了記録の書き込み後、動作の前 | 実行漏れ |
| 先に実行し、その後で完了を記録 | 動作の後、完了記録の前 | 重複実行 |

ローカルのSQLiteトランザクションで保護できるのはローカルの記録だけで、離れた場所にある照明器具の物理的な動作まで同じトランザクションに含めることはできません。より強い保証には、実行側でのリクエストの重複排除や、照会可能な操作結果などの仕組みと、両者のプロトコル上の連携が必要です。オートメーション内のフラグ一つだけでは実現できません。

## 実験：同じように二度再試行しても、`off`と`toggle`では逆の結果になる

最初は点灯している模擬照明を用意し、期限を600とするタスクを作成して、模擬時刻700に実行を試みます。

障害点は、照明が動作を受け取った後、タスクが完了として書き込まれる前に置きます。この時点でスクリプトはデータベース接続を閉じ、再び開きます。次回の実行プログラムから見える永続化状態を模擬するためです。時刻の値は人為的に与えた整数であり、実測した秒数ではありません。OSを実際に停電させてもいません。

復旧後もタスクは実行待ちなので、再び試みます。

今回の実行結果は次のとおりです。

```text
crash_after_action_off     calls=2  lamp_on=false
crash_after_action_toggle  calls=2  lamp_on=true
```

消灯操作を二度続けて実行しても、模擬照明は最終的に消えたままです。一方、切り替え操作を二度実行すると、模擬照明は最終的に再点灯します。

したがって、**復旧時の再試行を許すタスクでは、「切り替え」よりも「消灯」のように目標状態を明示する操作を優先すべきです。** この小さな場面での冪等性の実際的な価値は、そこにあります。

ただし、無制限に再試行してよいわけではありません。二度の`off`の間にユーザーが手動で点灯したなら、二度目の操作はユーザーの意図に反する可能性があります。実機では、重複したコマンドが追加の動作やイベントを引き起こす可能性もあります。検証したのは模擬照明の真偽値に関する冪等性だけであり、機器の電気的な挙動や、オートメーションのあらゆる副作用ではありません。

## 復旧後に見える「無人」も、古い値かもしれない

起動時にセンサーの状態が`off`と読めても、確認すべきことがあります。これは起動後に受信した新しい観測でしょうか。それとも復元された古い状態でしょうか。

実験では、観測に次の三つの条件を求めます。

```text
無人であることが明示的に報告されている
報告の受信時刻が今回の起動時刻より前ではない
現在の判断時刻から、モデルで定めた鮮度の範囲内にある
```

スクリプトでは、境界をテストするために30模擬時間単位を鮮度の範囲としています。すべての実機に30秒を推奨しているわけではありません。実際の閾値は、機器の報告周期と業務上の影響に応じて決めるべきです。

実験では、起動前の古い`off`、`unknown`、`on`、鮮度の範囲を超えた`off`をそれぞれ入力しましたが、いずれも消灯を呼び出しませんでした。新たに受信し、かつ範囲内にある`off`だけが実行を許可しました。

ここには、統合層での実際の難しさも表れています。状態が変わったときにしか報告しない機器もあれば、キャッシュを復元するインテグレーションもあります。また、読み取り操作が必ずしも機器へ直接アクセスするとは限りません。したがって、任意のエンティティの時刻フィールドだけで「ハードウェアがたった今、無人を再確認した」と証明できるとは考えないでください。具体的な機器に接続する際は、そのデータの出所を確認する必要があります。信頼できる新しい観測が得られないなら、待機を続けるか、人による対応を選びます。

`unknown`も`unavailable`も、「`on`ではない」という判定で無人に変えてはいけません。

## 古いタスクの完了通知で新しいタスクを消してはいけない

最初のカウントダウンが終わる前に、ユーザーがより遅い消灯時刻を設定し直すことがあります。このとき、古いコールバックが「グローバルな`pending`を`false`にする」と、新しいタスクまで消してしまう可能性があります。

実験ではタスクごとに異なるIDを割り当て、条件付き更新を使います。

```sql
UPDATE job
SET state = 'done'
WHERE id = ? AND state = 'pending';
```

新しいタスクの作成時には、古い実行待ちタスクをキャンセルしてから新しいタスクを挿入します。この二つの処理は、同一のSQLiteトランザクション内で行います。古いタスクの完了通知が持つのは古いIDだけなので、新しいタスクを完了に書き換えることはできません。

実験では、古いタスクのIDは1、期限は600で、新しいタスクのIDは2、期限は900です。古いタスクの完了コールバックが到着した後も、時刻700には実行可能なタスクがなく、時刻901にはタスク2を取得できました。

ただし、タスクIDが守れるのは記録だけです。**すでに機器へ送られた古いコマンドは取り消せません。** 古いリクエストがまだネットワーク上にあり、新しいタスクの作成後に機器がそのリクエストを実行すれば、新しい意図に反する可能性があります。実際のシステムでは、処理の直列化、キャンセルの意味、実行側でのバージョン確認をさらに検討する必要があります。この記事の単一実行者モデルは、ネットワーク上の並行するコマンドの問題を解決していません。

## Home Assistantと接続する際に必要な確認の契機

通常の時刻トリガーに加え、少なくとも起動後と重要なエンティティの復旧後にも確認する必要があります。取り逃した起動契機に備え、バックグラウンドで低頻度の予備確認を設けることもできます。確認のたびにタスクの状態を読み取り、「トリガーされた」ことをそのまま「実行すべき」と同一視してはいけません。

公式のTimerドキュメントには、`restore`を有効にするとアクティブまたは一時停止中のタイマーを復元できる一方、停止中に期限が来たタイマーについては、起動時に`timer.finished`が後から発行されないと明記されています。[2] 状態トリガーのドキュメントにも、再起動またはオートメーションの再読み込みによって`for`がリセットされると明記されています。[3]

これらの事実は復旧時の確認が必要なことを示しますが、次の判定が無条件に安全だという意味ではありません。

```text
現在時刻が古い期限を過ぎている → 無条件に消灯
```

復旧時には、タスクがまだ有効か、対象機器が存在するか、現在の条件が許すか、状態を示す証拠が十分新しいか、明示的な手動操作による上書きがないかを併せて確認すべきです。

時計が信頼できない場合、機器が長期間利用できない場合、失敗が続く場合などについては、自動試行を止める境界も定義する必要があります。このモデルには、最大再試行回数、バックオフ、アラートは実装していません。実際に接続する前に追加する必要があり、無制限に送信してはいけません。

## 再現できる結論

付属ファイルは`deadline_lab.py`です。Python 3の標準ライブラリを使用し、一時的なSQLiteデータベースは実行終了後に削除します。Home AssistantのTokenは不要で、実機にもアクセスしません。

```sh
python deadline_lab.py
```

今回、4組のシナリオのアサーションが通り、結果を`deadline_results.json`に保存しました。

| シナリオ | 検証できた事実 |
| --- | --- |
| データベースを閉じて開き直し、条件を確認 | 実行待ちタスクは残る。古い観測、不明な観測、在室中の観測、鮮度の範囲を超えた観測は遮断され、有効な新しい観測で動作が一度発生する |
| 動作後、完了の書き込み前に中断し、`off`を再試行 | 実際に二度呼び出され、模擬照明は最終的に消灯 |
| 同様に中断し、`toggle`を再試行 | 実際に二度呼び出され、模擬照明は最終的に点灯 |
| 新しいタスクで古いタスクを置き換え、その後に古い完了通知が到着 | 古い完了通知は新しいタスクを完了させない |

この4組の結果は、停電時の永続性も、Home AssistantのヘルパーがSQLiteのトランザクションと同じ意味を持つことも、複数実行者が並行する場合の正しさも証明しません。実験ではむしろ、「動作は実行されたが状態はコミットされていない」という隙間を意図的に残し、ローカルの記録だけでは「ちょうど一度だけ実行する」と約束できない理由を示しています。

家庭の普通の照明なら、復旧後に現在の条件を確認し、必要なら明示的な消灯指示を再送し、キャンセル手段を用意するという判断を受け入れられることが多いでしょう。決済、解錠、一度きりの材料投入など、気軽に繰り返せない動作では、同じ判断がまったく成り立たないかもしれません。

タイマータスクを設計する際に本当に明確にすべきなのは、システムが動作結果を忘れた瞬間、実行漏れと重複実行のどちらをより許容できないかです。それを明文化して初めて、復旧ロジックに検証可能な目標ができます。
