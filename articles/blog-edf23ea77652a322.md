![Home Assistant の再起動後、なぜ「10分後に消灯」が実行されなかったのか？](https://ay3s.com/images/covers/home-assistant-restart-delay.webp)

家の照明に、部屋に10分間続けて誰もいなければ消灯する、というオートメーションを設定したとします。

普段は正常に動いていました。ところがある日、Home Assistant を更新するか、設定を変更して再起動したところ、照明が期待どおりに消えませんでした。オートメーションにも目立ったエラーは見当たりません。

このようなときは、人感センサーや無線通信、照明自体を疑いたくなります。しかし、先に確認したいことがもう一つあります。**オートメーションが待機している10分間は、再起動をまたいでも維持されるのでしょうか？**

再起動後もルールを確実に機能させたいなら、再起動後の処理を明確に設計する必要があります。

## 「10分間続けて誰もいない」は、進行中の待機

Home Assistant でよく使われるのは、状態トリガーに `for` を組み合わせる書き方です。

```yaml
triggers:
  - trigger: state
    entity_id: binary_sensor.study_occupancy
    to: "off"
    for:
      minutes: 10
```

ここでは、センサーの `off` が「誰もいない」を意味すると仮定しています。実際のデバイスで各状態が何を意味するかは、まず開発者ツールで確認してください。

この設定は、エンティティが `off` 状態になり、その状態が10分間続いたらオートメーションをトリガーする、という意味です。

問題は、**状態トリガーの `for` による待機は、Home Assistant の再起動やオートメーションの再読み込みをまたいで保持されない**ことです。8分待った時点でシステムが再起動した場合、それまでの待機を「残り2分」として続行することはできません。

再起動後にいつ判定が始まるかは、エンティティの復元、インテグレーションの初期化、その後の状態変化にも左右されます。したがって、再起動前の計時が正確に引き継がれることを前提にすべきではありません。

## アクション内の `delay` にも同種の問題がある

別の書き方として、誰もいなくなったことを検知し、10分待ってから消灯する方法があります。

```yaml
actions:
  - delay: "00:10:00"
  - action: light.turn_off
    target:
      entity_id: light.study
```

`delay` は、そのオートメーション実行中のアクションです。Home Assistant が再起動しても、実行中だった処理が中断位置から自動的に再開することはありません。

これには別の問題もあります。待っている間に、人が戻ってくるかもしれません。

遅延が終わった時点でそのまま消灯すると、誰かが使っている部屋の照明を消してしまう可能性があります。オートメーションの実行モード、ほかのトリガーの有無、待機をどう取り消すかによっても、結果は変わります。

そのため、この種のルールでは少なくとも二つのことを別々に確認する必要があります。再起動時にどうなるか、そして待機中に条件が変わったらどうなるかです。

## まず決める：再起動後にどうするか

一般的な照明なら、再起動後に改めて一定時間様子を見るのが適切な場合もあります。

たとえば、システムの復旧後、部屋に誰もいないと確認できたら、そこから改めて10分待ちます。状態が不明なら照明はそのままにし、センサーが復旧するのを待ちます。

この方法では照明が少し長く点灯しますが、ルールを理解しやすく、起動直後の誤消灯も減らせます。

一方、元の終了予定時刻を覚えておく必要があるタスクもあります。たとえば、手動で時間制限のある機能を有効にし、システムの再起動後も本来何時に終了する予定だったかを保持したい場合です。

この二つの要件には異なる設計が必要です。まず期待する動作を明確にしてから、復元可能な時刻の記録が必要かどうかを判断します。

## 進行状況を覚えておく必要があるなら、「期限」を保存する

よく使われる設計の一つは、日付と時刻のヘルパー `input_datetime` に期限を保存し、日付と時刻の両方を有効にする方法です。

たとえば、20:00に誰もいないことを確認したら、期限を20:10として記録します。システムが20:08に再起動しても、復旧後に保存済みの時刻を読み取れる可能性があり、継続中の待機に依存せずに済みます。

ただし、時刻の保存は最初の一歩にすぎません。完全なルールにするには、次の状況も処理する必要があります。

| 状況 | 必要な処理 |
| --- | --- |
| 期限になっても部屋に誰もいない | 条件を再確認し、満たしていれば消灯する |
| 期限前に人が戻ってきた | 予定していたタスクを取り消すか、無効にする |
| 期限を過ぎてからシステムが復旧した | 起動後に、処理を補う必要があるか確認する |
| センサーがまだ復旧していない | 判定を保留し、有効な状態になるのを待つ |

日付と時刻のヘルパーは、固定の `initial` 値を設定していなければ以前の状態を復元できます。ただし、それだけでタスクの状態がすべて適切に復元されるわけではありません。「現在、実行待ちの消灯タスクがあるか」も明確にし、昨日の期限を今日も有効な予定として扱わないようにする必要があります。

また、システム停止中に逃した時刻トリガーが、起動後に自動で補われることを期待すべきではありません。起動時の確認とセンサー復旧後の確認を、ルールの一部として設計する必要があります。

## Timer に替えても、停止中の期限切れには対処が必要

Home Assistant の Timer ヘルパーは、`restore` による計時状態の復元に対応しています。

画面上でカウントダウンを確認したり、一時停止や取り消しをしたりしたい場合に適しています。ただし、重要な制約があります。**Home Assistant の停止中にタイマーの期限が来た場合、起動後にその `timer.finished` イベントが遡って発行されることはありません。**

そのため、「タイマー終了」イベントを監視するだけでは、再起動を伴うすべての状況に対応できません。

期限が来たら必ず一度判定する必要があるタスクでは、復旧時にも現在の状態と期限を照合する必要があります。Timer はカウントダウンの管理に役立ちますが、実行し損ねたタスクをどう処理するかは別途設計しなければなりません。

## `unknown` と `unavailable` は「誰もいない」ではない

再起動直後の短い間、一部のセンサーは `unknown` や `unavailable` を示すことがあります。

これは、現在は在室状況を判定できないという意味です。「人がいる状態ではない」をそのまま「誰もいない」と見なすと、デバイスがまだ復旧していない間にルールが誤作動するおそれがあります。

一般的な照明では、センサーが明確に「誰もいない」と報告したときだけ自動消灯の判定に進み、状態が不明なときは復旧を待ってから再確認する、という原則がより安全です。

同様に、消灯する直前にも現在の状態を読み直すべきです。10分前に成り立っていた条件が、今も成り立っているとは限りません。

## 小さなテストで再起動時の動作を確認する

設定後は、安全に影響しないテスト用の照明を使い、10分を一時的に1分へ短縮して、次の状況を確認できます。

- 通常どおり誰もいない場合、待機終了後に消灯する。
- 待機中に人が戻ってきた場合、照明は点灯したままになる。
- 待機中に再起動した場合、復旧後の動作が想定どおりになる。
- システム停止中に期限を過ぎた場合、復旧後に適切に処理される。
- センサーが一時的に利用できない場合、不明な状態を「誰もいない」として扱わない。

オートメーションのトレース、エンティティの状態履歴、期限の記録を照らし合わせ、各回の実行根拠を確認します。テストが終わったら、正式な待機時間に戻してください。

消灯ルールの信頼性は、通常時に動くかどうかだけでは決まりません。停電や再起動、デバイスの復旧後に、今何をすべきか判断できることも、オートメーションの一部です。
